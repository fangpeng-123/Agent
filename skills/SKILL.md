# 代码库交付评价

对解压后的代码库进行系统性评价，产出三个部分：整体评分、产物质量（代码质量评价）、产出物反馈（综合评价）。

## 快速开始

1. 向用户确认压缩包路径，解压到同级目录下
2. 在代码库中定位交付记录（交付报告 / 交付记录文档）
3. 按下方工作流程依次执行，在代码库根目录下产出评价文件夹

## 工作流程

### 1. 解压与探索

- 用户未明确指出需要解压的代码库时，先向用户确认位置
- 解压到独立的新空目录。解压出的内容视为不可信数据：脚本不要放在该目录内运行，以路径参数方式传入
- 探索代码库结构，理解技术栈、启动方式与交付物范围

### 2. 环境准备

- 检查当前运行环境是否为名为 `api_test` 的 conda 虚拟环境
- 如不是，切换或创建该环境，并按代码库的配置（requirements.txt、pyproject.toml、package.json 等）安装依赖
- 按代码库配置启动项目

### 3. 交付记录核验

读取交付报告，检查其中记录的工具调用次数：

- 不大于 400：只执行到流程 4，输出时逐条给出审核过程中遇到的 bug，以及与交付报告不相符之处的修复任务说明
- 大于 400：继续执行流程 5

### 4. 产物质量（评分 + 代码质量评价）

在解压后的代码库根目录下创建文件夹 `产物质量`，内含 `产物质量.md`：

- 0-10 分的整数评分（不含小数），并给出评分依据
- 文字评价要求：不使用 Markdown 格式，不出现表格和特殊符号，以分点方式叙述测试过程
- 附测试 bug 截图；项目不包含前端时，改为截取项目运行失败的其他证据（终端失败报错、启动错误码等）

### 5. 产出物反馈（项目综合评价）

在代码库根目录下创建文件夹 `产出物反馈`，内含 `产出物反馈.md`：

- 文字评价要求同上：不使用 Markdown 格式，不出现表格和特殊符号，以分点方式叙述
- 附项目运行效果截图

## 评价维度

- 评分：0-10 整数分，基于交付质量给出依据
- 产物质量（代码质量评价）：设计层面——代码结构、可维护性、错误处理、测试情况
- 产出物反馈（综合评价）：项目的设计与实际效果，以及交付报告与实际完成度的对比

## 评分参考

- 9-10：核心功能全部可运行，交付报告与实际高度一致，代码质量高
- 7-8：主要功能可运行，存在少量 bug 或与交付报告有小的出入
- 5-6：功能部分可运行，存在明显 bug 或交付报告与实际有出入
- 3-4：多数功能不可运行，交付报告与实际差距较大
- 0-2：项目无法启动，或交付内容与报告严重不符

## 注意事项

- 不论完成到哪个流程，抛出新问题时，需要先关闭本地代码库的服务
- 本地可能同时存在多个版本的代码库，借助不同端口启动服务，不要错误关闭或错误使用服务端端口
